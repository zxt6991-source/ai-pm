一、产品概述

1.1 项目背景

跨境电商支付链路涉及国家地区、支付方式、支付渠道、终端环境、SDK 版本、风控及第三方支付服务等多个维度。

当支付成功率发生异常波动时，运营与技术支持人员可能需要分别查询支付统计、失败错误码、版本发布记录和故障知识库，再通过人工经验判断异常原因。

该流程存在三个有待验证的问题：

  1. 数据分析流程复杂： 不同支付渠道和客户端的失败数据需要多维度组合分析。
  2. 故障知识分散： 错误码说明、SDK 文档、历史处理经验难以在一次分析中完成关联。
  3. 诊断依赖人工经验： 新人难以快速判断异常线索，资深人员需要重复处理相似问题。

传统 BI 看板可以展示支付成功率和错误率，但对跨系统、多步骤的自然语言诊断任务支持有限。

PayPilot AI 计划通过 AI Agent 将指标查询、异常分析、知识检索和报告生成整合为一套可追溯的工作流。

1.2 产品定义

PayPilot AI 是一款面向支付运营人员和支付技术支持人员的 AI 智能诊断助手。

用户可以直接用自然语言提出问题，例如：“德国地区的 Klarna 支付成功率为什么下降？”

系统通过结构化数据查询、异常维度分析和支付知识库检索，识别潜在异常原因，生成带有数据证据、知识引用和建议行动的诊断报告。

产品强调 可解释、可追溯、可验证和人工可控，不将大模型判断直接作为真实支付策略的执行依据。

1.3 产品价值主张

核心价值：从人工跨系统排查，转变为 AI 辅助的结构化支付异常诊断。

价值方向 预期价值
提升运营效率 减少人工重复查询、筛选和归纳数据的步骤
降低排查门槛 通过自然语言查询与结构化报告降低工具使用成本
提升诊断一致性 统一指标口径、知识来源和诊断报告格式
提高知识复用率 将公开文档和模拟故障案例组织为可检索知识库
支持持续改进 通过反馈、Trace 和评测集识别 Agent 失败模式

二、用户研究与需求分析

2.1 目标用户

用户 A：支付运营专员

典型任务：日常支付指标监控、异常发现、问题初步定位、支付运营报告。

主要痛点假设：频繁切换地区、支付方式和终端维度；异常发生后不知道优先排查哪个环节；需要技术人员解释错误码；分析过程整理为报告较耗时。

核心诉求：快速识别异常、理解可能原因、获得下一步排查建议。

用户 B：支付技术支持工程师

典型任务：排查 SDK、回调、接口、第三方支付服务等故障。

主要痛点假设：需要关联客户端版本、支付错误码和交易链路日志；历史问题和渠道文档分散；重复解释类似故障；不易追溯诊断依据。

核心诉求：获得结构化异常线索、可信证据和明确的技术排查方向。

用户 C：支付运营负责人

典型任务：跟踪重点地区支付表现、协调异常处理、评估团队效率。

核心诉求：了解异常影响范围、诊断进度及 AI 工具的实际提效效果。

2.2 用户研究计划

MVP 开发前，计划完成 3～5 次半结构化访谈。访谈对象优先选择具有支付运营、交易系统监控或支付技术支持经验的人员。

访谈问题：

  1. 最近一次支付成功率异常是如何发现的？
  2. 从发现异常到定位原因，需要使用哪些数据与工具？
  3. 哪个环节最耗时，为什么？
  4. 在什么情况下需要升级给研发或第三方支付渠道？
  5. 如果 AI 提供诊断结果，你需要看到哪些证据才会相信它？
  6. 哪些操作可以交给 AI，哪些必须人工确认？

研究输出：访谈纪要、现状任务流程、痛点优先级、AI 机会点及假设验证清单。

若无法访谈真实业务人员，需要在作品集中标注限制，不能将模拟访谈当作实际调研成果。

2.3 核心需求定义

采用“用户任务—痛点—产品机会”整理：

用户任务 现有问题假设 产品机会
查看支付成功率 查询筛选步骤繁琐 多维指标看板
判断异常是否值得关注 需要人工设定对比维度 自动基准对比与异常标记
查找异常集中区域 需要手动下钻多个维度 Agent 驱动的分群分析
理解支付失败 错误码和技术知识分散 RAG 知识检索
形成处理建议 分析过程依赖经验 有证据的诊断报告
复盘诊断质量 缺乏统一反馈记录 评测与 Bad Case 管理

2.4 JTBD 用户任务描述

当支付运营人员发现某地区、某支付方式成功率异常时，希望系统帮助其快速确认异常范围、找到潜在原因，并提供可以交由技术团队进一步核查的证据和建议，以便降低排查成本和沟通成本。

三、产品目标与成功指标

3.1 业务目标

在 MVP 的模拟环境下，验证 AI Agent 是否能够在支付异常分析任务中，相比人工操作 BI 与知识库的流程，提供更高效且具备可信证据的诊断体验。

主要目标：缩短典型异常分析时间；提高异常类别识别能力；让诊断结论具备可追溯依据；验证自然语言交互的实际使用价值。

非目标：MVP 不承诺直接提高真实支付成功率，不自动替换支付渠道，不自动调整风控规则，不自动执行退款或补单，不替代支付研发与运维人员的最终故障判断。

3.2 北极星指标

有效诊断完成率：在全部发起的可评估诊断任务中，用户认为结果可用于理解异常或推进下一步排查，且结果具备有效证据的任务比例。

有效诊断完成率 = 符合业务有效性与证据要求的任务数 / 全部可评估诊断任务数 × 100%

需要区分：

  • 技术完成：Agent 成功执行并输出。
  • 结果正确：诊断分类与标准答案一致。
  • 业务有效：输出能够帮助用户做出合理的下一步判断。

三者不能混为一谈。

3.3 核心指标

指标 定义 MVP 目标
诊断分类正确率 可判定测试样本中，异常类别判断正确的比例 ≥80%
Agent 工作流完成率 规定流程未发生非预期中断的任务比例 ≥90%
证据引用有效率 被评审为确实支持相应判断的证据引用比例 ≥95%
人工诊断耗时变化 AI 辅助与人工基线的完成时间对比 目标减少 ≥50%
工具调用成功率 有效工具调用成功次数 / 总有效调用次数 ≥95%
高风险越权操作数 未经授权的数据访问或交易修改 0
单次诊断成本 模型调用及相关推理服务成本 / 完成任务数 建立基线后设预算

以上是产品设计目标。正式结项时必须呈现实测样本、测试方法、结果及未达标项。

3.4 业务观察指标

支付成功率（PSR）、支付失败率、特定错误码占比、支付方式异常集中度等主要用于衡量支付场景状态。

PSR 不直接作为个人项目 MVP 的效果归因指标。 若没有真实线上策略干预和可比实验条件，不能宣称 AI 系统改善了真实支付成功率。

4.2 MVP 范围约束

第一版仅要求完成一个典型支付异常场景，从用户提问到形成可追溯报告，再到反馈和评测的完整闭环。不追求一次性接入全部支付方式、全部数据平台和所有类型的 Agent。

五、核心业务场景

5.1 场景 S01：支付成功率异常定位

场景名称：德国 Klarna 支付成功率下降。

用户角色：支付运营专员。

触发条件：支付看板显示德国地区 Klarna 支付成功率相较基准下降。

用户输入：“帮我分析德国 Klarna 过去 24 小时支付成功率下降的原因。”

预期系统行为：

  1. 解析地区、支付方式、时间范围等参数。
  2. 查询当前统计周期的成功支付尝试数和有效支付尝试数。
  3. 查询基准周期，并计算成功率差异。
  4. 按终端、应用版本、失败阶段、错误码等维度下钻。
  5. 识别异常贡献较高的维度。
  6. 检索相关支付错误码或 SDK 故障知识。
  7. 整合量化证据和知识证据。
  8. 输出可能原因、无法确认的事项及建议行动。
  9. 允许用户继续追问并提交诊断反馈。

成功标准：用户能够理解异常发生在哪里、哪些判断有证据、还需要验证什么。

5.2 场景 S02：具体错误码解释

用户输入：“redirect_timeout 是什么意思？应该怎么排查？”

系统应优先检索错误码知识，并结合用户是否提供具体渠道、SDK 版本等信息决定是否继续追问。

预期输出：错误码解释、适用范围、常见排查方向、引用文档和待确认条件。若知识库没有可信资料，禁止编造特定支付渠道的官方错误码含义。

5.3 场景 S03：多维度异常对比

用户输入：“对比德国地区 Android 和 Web 的 Klarna 支付成功率，看看问题集中在哪里。”

系统展示两个终端的成功率、交易量、失败量、主要错误类型和变化幅度。

5.4 场景 S04：证据不足

用户输入：“为什么所有欧洲支付都失败了？”

系统需判断输入是否过于宽泛、数据样本是否充分。若缺失关键维度，优先请求补充；若数据无法支持结论，展示“当前证据不足”及需要继续查询的维度。

六、产品信息架构与交互流程

6.1 信息架构

  • 支付概览：核心指标、成功率趋势、多维筛选、异常维度下钻。
  • AI 智能诊断：自然语言输入、参数确认、执行进度、诊断结果、连续追问。
  • 诊断报告：异常摘要、数据证据、原因假设、建议行动、用户反馈。
  • 知识库：文档列表、文档检索、索引管理。
  • 评测中心：测试用例、运行记录、指标统计、Bad Case 分析。

6.2 核心用户流程

发现异常 → 发起诊断 → 参数确认 → Agent 执行分析 → 查看证据与报告 → 人工确认 → 提交反馈

状态 定义 前端表现
EMPTY 尚未发起任务 输入建议及示例问题
CLARIFYING 参数缺失或歧义 参数补充卡片
RUNNING Agent 正在执行 分步骤执行进度
COMPLETED 已生成可查看的报告 诊断结论与证据
INSUFFICIENT 数据不足以确认原因 已知事实与待核查项
FAILED 工具或系统发生错误 失败原因及重试入口
CANCELLED 用户主动停止任务 保留已完成的步骤

6.3 页面 P01：支付概览 Dashboard

目标：帮助用户发现异常、快速定位问题维度，并发起 AI 诊断。

顶部筛选：时间范围（24h、7d、30d、自定义）、地区、支付方式、终端（Web、Android、iOS）、客户端版本。

核心指标卡：支付成功率、有效尝试数、失败尝试数、较基准变化、待关注异常维度数。

数据展示：成功率趋势折线图、支付方式成功率对比、失败错误码 TOP N、地区/终端异常分布。

每个异常行提供“AI 分析”操作，并把当前筛选条件带到诊断页面。

验收：筛选联动准确；指标统一；数据不足有提示；参数传递准确；标明数据截至时间和模拟数据身份。

6.4 页面 P02：AI 智能诊断

目标：通过自然语言完成支付异常的多步骤分析。

布局：左侧任务历史；中部对话、参数确认、执行进度、结果摘要、追问；右侧证据面板（筛选、统计、错误码、文档、数据时间）。

交互规则：

  1. 输入问题立即展示已接收状态。
  2. 必要参数缺失时请求补充。
  3. 执行阶段展示用户可理解的步骤。
  4. 工具错误时限制重试，不无限循环。
  5. 允许停止执行；已完成的工具结果可查看。
  6. 支持基于当前报告继续追问。

验收：无需 SQL 即可完成指定任务；不虚构未查询数据；失败原因可理解；展示数值与工具查询一致。

6.5 页面 P03：诊断报告

目标：形成可供支付运营及技术支持共同使用的结构化结果。

报告结构：问题摘要、异常结论、影响范围、量化证据、可能原因、相关知识、建议行动、不确定性、反馈入口。

规则：数字由工具提供；关键判断要引用；区分事实与假设；不允许执行真实交易修改。

验收：可从报告追踪到对应数据或文档；无证据的判断不能标记为已确认根因。

6.6 页面 P04：知识库管理

支持导入允许使用的 Markdown、TXT、PDF 文档；展示标题、来源、适用方式、更新时间、索引状态；重建索引；关键词或语义检索测试；标记失效或冲突。MVP 优先支持 Markdown/TXT，PDF 解析作为可选增强。

6.7 页面 P05：AI 评测中心

支持查看测试集、执行批量评测、查看工作流完成率与分类正确率、对比 Prompt/Workflow 版本、查看错误样本和人工复核结果。强调可度量、可迭代，而非复杂平台。

七、详细功能需求

F01：支付模拟数据导入与管理（P0）

系统接收规范化模拟支付尝试数据，进行字段校验、重复记录检查和数据质量统计。输入是 CSV 或预置数据。

规则：每条尝试唯一 payment_attempt_id；同一订单可有多次尝试；必填缺失需标记；全部显式标记 DEMO；不得导入真实银行卡敏感认证数据或未经授权的客户信息；记录批次和数据版本。

输出：可供看板和 Agent 查询的标准化数据。

验收：数据导入后可查询交易量、支付结果、地区及方式；重复记录不重复统计。

F02：支付指标计算（P0）

PSR = 成功的有效支付尝试数 / 有效支付尝试总数 × 100%

MVP 口径：

  • SUCCESS：成功的终态支付尝试。
  • FAILED：失败的终态支付尝试。
  • PENDING：尚未形成终态。
  • CANCELLED：用户取消，默认单列、不纳入 PSR 分母，可按业务规则另行配置。
  • 有效支付尝试 = SUCCESS + FAILED。

为避免异步结果未回传导致统计偏差，仅对到达可配置观察成熟时间的数据进行比较，同时展示待决比例、数据延迟情况。生产口径需要依据业务重新确认。

维度：地区、支付方式、终端、客户端版本、错误码、失败阶段、时间区间。

验收：同数据、同筛选条件，Dashboard 与 Agent 指标一致。

F03：支付异常识别与分群（P0）

对指定支付范围做基准对比，发现值得关注的异常维度。

默认当前窗口：过去 24 小时的成熟数据。基准：前 7 个可比日期中相同时段的统计数据（支持用户修改）。

异常候选规则（同时满足）：

  1. 当前有效尝试数不少于 200。
  2. 相较基准成功率下降至少 3 个百分点。
  3. 当前与基准数据质量检查通过。

这代表需要关注的异常候选，不等同统计显著性检验结果，更不是根因确认。

下钻支付方式、终端、版本、错误码和失败阶段。输出当前与基准成功率、变化幅度、样本量及下钻入口。

验收：能定位预置异常；样本不足标记数据不足。

F04：自然语言意图识别（P0）

意图 输入示例
指标查询 查询德国今天的支付成功率
异常分析 为什么 Klarna 成功率下降
维度对比 比较 Web 和 Android 的失败率
错误解释 redirect_timeout 是什么意思
后续追问 这个问题是否集中在新版本
范围外请求 帮我直接切换支付渠道

参数字段：intent、region、payment_method、time_range、channel、app_version。

规则：能确定则自动解析；不会影响结论的维度可以使用明确默认值；关键歧义先确认；不擅自转换未知地区或方式；涉及真实交易修改时拒绝并解释。

验收：预置问题可正确识别核心意图和参数，歧义场景合理追问。

F05：Agent 数据工具调用（P0）

Agent 使用受控工具访问结构化数据，不具备任意 SQL 执行权限。

工具 用途
get_payment_metrics 获取 PSR、交易量等指标
compare_payment_periods 比较当前与基准周期
get_failure_breakdown 按终端、版本、错误码分群
get_error_distribution 获取错误码分布
get_release_changes 查询模拟版本发布记录
search_payment_kb 检索支付知识库

规则：工具只读；维度白名单；限制时间范围、返回量和扫描量；不暴露密钥；结果携带查询标识、样本量、数据版本、时间范围。

验收：多工具串联有效，越权和不可用工具被阻止并留痕。

F06：支付知识库 RAG 检索（P0）

来源：公开许可文档、自编演示错误码说明和模拟故障案例。元数据：文档 ID、标题、适用支付方式、来源、更新时间、版本、有效性。

检索流程：问题改写/关键词提取 → 混合检索或向量检索 → 相关性重排 → 返回片段 → 引用生成。

规则：优先当前支付方式和错误码；引用定位文档与片段；文档与结构化数据冲突时不得无根据定论；失效/不适用文档需标记；外部内容视为不可信输入，不得提升工具权限。

验收：有覆盖时找到适用资料；无覆盖时不编造来源。

F07：智能诊断与报告生成（P0）

工作流：任务理解 → 参数确认 → 指标查询 → 异常下钻 → 知识检索 → 证据核验 → 原因假设 → 报告生成。

报告最低字段：异常范围、统计结果、集中维度、证据来源、可能原因、替代解释、核查建议、不确定性。

根因规则：没有独立验证，仅使用“可能原因”“异常线索”“建议核查”。例如版本发布与成功率下降时间相近，不能单凭相关性确认因果。

报告前校验：数字来自已执行工具；引用存在；证据属于当前范围；推断没有越过证据；没有敏感越权操作。失败后可受控修复一次，仍失败则返回部分结果和错误提示。

验收：报告结构化、数字正确、可追溯且未确认原因不被写成事实。

F08：连续追问与上下文管理（P0）

例：“这个问题是否只发生在 Android 端？”“和最新版本发布有关吗？”继承当前任务地区、方式和时间，用户主动修改参数则覆盖。

规则：任务上下文隔离；追问记录实际查询范围；数据版本变化时提示重新分析；对话摘要不能代替证据。

验收：不错误继承其他任务，也不把旧结果冒充最新数据。

F09：诊断反馈与纠错（P0）

反馈：正确且有帮助、部分正确、错误、无法判断。

错误标签：数据不准确、原因判断错误、文档引用不适用、建议不可操作、响应过慢、工具失败、其他。

记录关联任务、Agent 版本、报告版本、反馈类别、说明。

验收：反馈关联具体执行记录，并可进入 Bad Case 管理。

F10：Agent 执行追踪与评测（P0）

记录任务 ID、问题及规范化参数、Workflow/Prompt 版本、工具调用顺序与耗时、检索文档 ID、输出报告、Token 与成本、护栏拦截及人工反馈。

验收：可复现关键失败并在相同数据集上对比版本。

F11：权限、安全与审计（P0）

MVP 角色：ANALYST 可查看演示指标、诊断、反馈；ADMIN 还可管理模拟数据、知识库和评测集。

限制：禁止真实交易写入、任意 SQL 和未经授权的敏感数据；输入及检索文本不能覆盖高优先级规则；防护 Prompt Injection；查询和管理操作留审计日志。

验收：越权、Prompt Injection、敏感泄露测试通过，不存在真实交易修改路径。

8.2 支付指标口径约束

  1. 支付尝试是统计单元，不能与订单数量直接混用。
  2. 同一尝试产生多条事件时，只计算一次。
  3. 当前与基准使用一致终态定义。
  4. 比较前检查延迟、成熟度和待决比例。
  5. 成功率变化使用百分点（pp），不能与相对百分比混用。
  6. 样本不足或质量异常时不做确定性根因判断。
  7. 显示统计时区和数据更新时间。

8.3 模拟案例数据

德国 Klarna 的演示数据：

指标 基准周期 当前周期
有效支付尝试数 4,000 2,000
成功支付尝试数 3,800 1,784
支付成功率 95.0% 89.2%
失败支付尝试数 200 216

成功率下降 5.8 个百分点。

终端 有效尝试 成功尝试 成功率
Android 1,000 850 85.0%
Web 1,000 934 93.4%

模拟中 Android 有 150 次失败，其中 90 次标记为 redirect_timeout。

可以支持的判断：Android 是重点排查对象，回跳超时为异常线索。

尚不可确认：不能仅凭分布确认 SDK、网络、渠道或发布变更是根因，需更多对比和链路证据。

九、AI Agent 产品方案

9.1 为什么选择 Agent

本场景需要基于前一步数据决定后续分析：总体 PSR 下降 → Android 下降更明显 → 查询 Android 错误码 → 检索知识 → 对比版本 → 报告。这是一条需要条件分支和多工具的工作流，而非单一 Prompt 生成报告。

9.2 系统逻辑架构

  • 用户层：Web Dashboard / AI Chat / 诊断报告 / 评测中心。
  • 产品服务层：任务管理 / 权限校验 / 会话上下文 / 报告管理。
  • Agent 编排层：Intent Parser → Planner → Tool Executor → Evidence Analyzer → Report Generator → Guardrail Validator。
  • 工具与数据层：支付指标查询 / 失败分群 / 发布记录 / RAG 知识检索。
  • 存储与可观测层：结构化数据库 / 向量数据库 / Trace 日志 / 评测数据。

9.3 推荐技术方案

层级 技术选型 选择依据
Web 前端 React + TypeScript 数据分析与对话交互
API 服务 FastAPI Python 工具和 AI 服务集成
Agent 编排 LangGraph 有状态流程、分支、重试、人工确认
结构化存储 PostgreSQL 支付模拟数据、任务、反馈
缓存 Redis（可选） 指标和任务状态缓存
RAG 向量检索 + Reranker 知识检索相关性
模型服务 可配置 LLM API 质量、成本与延迟对比
可观测 Trace + 结构化日志 问题复现
部署 Docker 演示环境复现

优先复用已有开发经验，减少额外基础设施成本。

9.4 Agent 节点定义

  1. Intent Parser：识别任务、提取范围、决定是否澄清。
  2. Plan Builder：决定工具调用，约束不必要工具链。
  3. Metrics Analyzer：执行指标查询和基准对比。
  4. Dimension Analyzer：执行多维度统计，定位集中区域。
  5. Knowledge Retriever：检索错误码、SDK 和模拟故障资料。
  6. Evidence Synthesizer：整合支持与反对原因假设的证据。
  7. Report Generator：按固定 JSON Schema 生成报告。
  8. Output Validator：检查数字、引用、表述和权限边界。

9.5 Agent 失败处理

失败类型 策略
意图不明确 请求澄清
查询失败 限次重试，停止相关分析
样本过小 说明不足并建议扩大范围
RAG 无匹配 不编造资料
检索文档冲突 展示冲突和适用范围
生成数字与工具不一致 校验失败，修复或降级
超时 告知状态，允许重新分析
Prompt Injection 忽略恶意指令，必要时阻断
请求修改真实交易 明确拒绝执行

9.6 人工接管机制

以下情况需人工判断：多个接近的原因假设、数据质量不足、涉及渠道配置/路由/风控、知识库无支持、连续执行失败、真实生产操作。

MVP 的人工接管为“建议转交人工 + 可复制证据摘要”，不实现真实工单系统。

十、AI 评测体系

10.1 评测目标

证明系统不仅能够调用工具，还能够提供正确、可引用、可解释、具有实际帮助的支付异常分析。

10.2 评测集设计

初始构建 100 条人工审核测试用例：

测试类型 数量
支付指标查询 20
支付异常诊断 25
多维度比较 20
错误码知识问答 15
数据缺失与歧义 10
对抗输入及安全边界 10
总计 100

每个测试样本应包含标准结果、允许的原因类别、预期工具和需要拒答的条件。

10.3 评测维度

  • 意图识别正确率：正确识别任务与参数的比例。
  • 数据准确率：模型输出数据与确定性查询保持一致的比例。
  • 诊断分类正确率：具备标准答案时异常分类正确的比例。
  • 证据引用有效率：引用是否真实支持判断，而非仅存在。
  • 正确拒判率：证据不足时能够准确说明不确定性的比例。
  • 工作流完成率：任务完成预定流程且无非预期失败的比例。
  • 响应时间与成本：端到端延迟、工具耗时、Token 和费用。

10.4 评测方式

离线评测：固定测试集批量执行，不同模型和工作流版本使用一致输入。

人工评审：对诊断正确性、证据相关性、建议可操作性进行复核。

对照实验：测试人员分别使用传统数据看板和 AI 辅助方案完成相同任务，对比耗时、正确率和主观易用性。

样本量少时仅报告描述性结果，不外推为真实业务提升。

10.5 Bad Case 迭代流程

收集失败用例 → 分类归因 → 定位失败节点 → 调整关键策略 → 回归测试 → 记录变化。

错误类型：意图识别、错误工具、查询参数、指标计算、召回不足、错误引用、过度推断、不合理建议、输出结构问题。

每次迭代应保存变更说明与同一测试集结果。

十一、埋点与数据分析需求

事件名 触发 用途

diagnosis_clarification_requested 请求补充参数 意图理解问题

11.2 产品分析问题

用户最常发起哪些任务？哪些任务易发生歧义？哪些工具拖慢响应？哪些异常类别正确率最低？有证据的报告是否更易获得认可？AI 是否缩短人工完成时间？

十二、非功能性需求

12.1 性能

  • Dashboard 常规筛选 P95 目标 ≤3 秒。
  • AI 诊断发起后尽快显示任务接收状态。
  • 分别统计知识问答和多工具诊断延迟。
  • 多工具诊断端到端 P95 目标 ≤30 秒。
  • 单工具设置超时，限制无界等待。
  • 记录主动取消和超时任务。

这些为演示环境目标，需按实测调整。

12.2 稳定性

工具失败可定位；模型结构校验失败应降级；任务状态可查询；已完成报告不得被异步无提示覆盖；重试避免重复创建/覆盖。

12.3 安全与隐私

仅使用模拟或授权数据；原始银行卡敏感数据不进模型上下文；日志不保存密钥和非必要个人信息；权限、工具白名单、参数校验控制访问；明确第三方模型数据处理范围；日志保留期可配置；不得宣称获得未取得的支付安全认证。

12.4 可观测性

每个诊断任务生成 Trace ID，可关联工具、耗时、错误、模型/工作流版本和报告版本。

十三、典型异常与边界场景

场景 处理
“成功率下降了” 追问地区、时间或方式
样本不足 不做高确定性异常判断
最新交易仍待决 展示数据延迟和待决状态
统计口径不同 阻止直接比较或提示
知识库没有错误码 不编造解释
文档过期 标记版本不匹配
多个可能原因 展示不同假设和证据
恶意 Prompt 不执行越权指令
请求切换渠道 说明只读诊断限制
追问变更时间范围 重新计算不沿用旧数值
某维度全部缺失 展示证据不足及需补充项
用户关闭页面 持久化任务可恢复查看

十四、MVP 研发计划

第 1 周：需求研究与产品设计

任务：访谈与排障流程梳理；痛点和优先级；PRD 评审；数据模型；页面低保真原型。

交付：研究记录、PRD、用户流程、信息架构、低保真原型。

第 2 周：模拟数据与交互原型

任务：构建数据和已知异常；完成 Dashboard、对话交互；演示知识库；诊断报告结构。

交付：模拟数据集、知识文档、核心原型、验收清单。

第 3 周：Agent MVP 实现

任务：支付查询 API、Agent 工作流、RAG、报告校验、Trace/反馈记录、护栏及错误处理。

交付：可运行 MVP、接口说明、流程图、基础测试报告。

第 4 周：评测与产品迭代

任务：构建复核 100 条用例；离线测试；用户反馈；Bad Case；至少一轮改进；作品集。

交付：评测报告、迭代记录、演示脚本、原型、面试作品集。

十五、验收标准与上线门槛

15.1 功能验收

  • 可导入/加载规范化模拟支付数据。
  • Dashboard 统一口径展示支付指标。
  • 用户可自然语言发起诊断。
  • Agent 能调用数据与知识检索工具。
  • 系统输出带证据的结构化诊断报告。
  • 支持连续追问和反馈。
  • 可查看 Trace 和评测结果。
  • 不可执行未授权支付交易修改。

15.2 质量验收

  • 执行并复核 100 条预设用例。
  • 可判定场景的诊断分类正确率达到目标。
  • 关键量化数据与工具结果一致。
  • 引用有效率达到目标。
  • 安全和越权测试无高风险问题。
  • 关键流程无阻断性缺陷。

未达标时记录差距，不可更改口径掩盖问题。

15.3 用户体验验收

针对典型排障任务对比人工与 AI 辅助流程，记录完成时间、正确性、人工步骤、信任程度、可解释性评价。

15.4 演示验收

稳定演示：支付成功率异常 → AI 诊断 → 指标下钻 → 错误码检索 → 证据报告 → 用户追问 → 评价反馈。

十七、Demo 演示场景

17.1 用户发起诊断

“德国 Klarna 最近 24 小时支付成功率为什么下降？”

17.2 系统查询

Agent 获取模拟数据：当前有效尝试 2,000；PSR 89.2%；基准 PSR 95.0%；变化 -5.8pp；Android 85.0%；Web 93.4%。Android 150 次失败中，90 次 redirect_timeout，占 Android 失败的 60%。

17.3 诊断报告示例

异常摘要：德国 Klarna 当前 PSR 为 89.2%，较基准下降 5.8pp。

异常线索：Android PSR 为 85.0%，低于 Web 93.4%；Android 当前 150 次失败中 90 次为 redirect_timeout；应优先排查 Android 支付回跳链路。

可能原因：Android 回跳流程异常是值得优先验证的假设，但仅凭当前数据无法确认特定 SDK 版本、网络或渠道状态是根因。

建议行动：

  1. 对比基准错误码占比和绝对次数。
  2. 按客户端版本进一步分析。
  3. 检查支付发起、跳转、返回与状态确认。
  4. 查询版本变更和故障日志。
  5. 配置变更须由授权人员复核。

诊断状态：初步分析完成，根因未确认。

17.4 用户继续追问

“是否和 Android 最新版本有关？”Agent 查询模拟发布记录和各版本失败分布。即使与发布时间接近，也只能报告相关性，不能证明因果。

17.5 用户提交反馈

选择“部分正确”，备注：“找到了 Android 回跳问题，但没有足够证据证明具体 SDK 版本存在故障。”系统关联该反馈与当前任务，进入 Bad Case 分析。

十九、后续版本方向

V1.1：提升诊断质量

扩展异常类型、增强分群归因、补充数据质量检查、优化知识检索、完善对话记忆和报告结构。

V1.2：运营工作流集成

异常通知、待处理工单、多人协作、处理进度跟踪、人工复核结果闭环。

V2.0：支付智能优化辅助

探索支付路由优化建议、渠道健康度评价和策略模拟。

任何真实支付策略变更都必须有独立的权限、审批、灰度、审计和回滚机制。严格区分“AI 提建议”与“系统执行策略”。

二十、项目结项与 AI PM 作品集要求

项目最终不仅交付软件，还应交付证明产品经理能力的材料：

  • 产品发现证据：目标用户、访谈、痛点、机会判断。
  • 产品定义证据：PRD、优先级、MVP 边界、关键取舍。
  • 产品设计证据：流程图、低高保真原型、交互规范。
  • AI 方案证据：Agent 架构、工具策略、RAG、护栏、人工确认。
  • 产品验证证据：评测集、对照测试、结果、Bad Case。
  • 迭代复盘证据：版本变化、失败归因、已验证改善和剩余问题。

完整闭环：业务问题发现 → 产品方案设计 → AI MVP 实现 → 评测验证 → 迭代优化 → 产品价值复盘。

产品原则：准确的数据 > 可靠的证据 > 可用的诊断建议 > 复杂的 Agent 自主能力。先证明比传统流程更高效、可信，之后再考虑自动预警、协作和支付优化建议。
