01 / PRODUCT FLOW

下一阶段要实现什么？

把此前原型中的“模拟 AI 执行”升级为真实后端数据查询、LLM 驱动的分析编排与可追溯报告。建议只围绕一个最小场景打通全流程。

01
用户提出支付异常问题“德国 Klarna 成功率为什么下降？”
02
Agent 调用真实数据查询接口从模拟支付数据库计算 PSR、与基准期比较、定位异常维度
03
Agent 检索支付知识库关联标准化错误码、SDK 文档与故障案例，保留来源
04
生成结构化、可溯源的诊断报告区分量化事实、待验证假设、建议行动和证据不足
05
用户追问、反馈与 AI 评测记录 Trace、准确率、执行耗时、成本与 Bad Case

阶段成功标志：每一项关键数字可复算，每一条判断可追溯，失败场景能被测试和改进。

架构原则：不要把“会执行工具”当成“分析正确”。查询结果必须来自确定性代码；LLM 不直接计算核心支付指标，更不能将时间相关性自动解释为故障因果。
03 / DELIVERY PLAN

四周研发与验证计划

每一周都有明确的可验收交付物。若时间紧张，优先保证端到端闭环，再逐步扩展支付方式和分析能力。

WEEK 01DATA FOUNDATION

建立真实数据分析能力

把静态演示数字变成真实数据库计算的结果。

  • 生成 1 万～5 万条可重复的模拟支付尝试数据。
  • 覆盖德国 Klarna、Android / Web、错误码与 SDK 版本。
  • 预置已知异常场景与标准答案。
  • 完成 PSR、时间比较、按终端和错误码下钻 API。
  • 校验统计口径、重复支付尝试和异常样本。
交付： PostgreSQL 数据库、数据脚本、指标接口、单元测试
WEEK 02AGENT RUNTIME

实现真正的 AI Agent

让工作流依据数据和证据给出结构化结论。

  • 实现意图解析与关键参数确认。
  • 接入支付指标、分群分析和知识检索工具。
  • 使用 LangGraph 串联固定的可控分析流程。
  • 生成符合 JSON Schema 的诊断报告。
  • 加入数值校验、证据校验、超时与降级。
交付： 单场景可运行 Agent、结构化报告、证据引用
WEEK 03PRODUCT EXPERIENCE

交互原型接入真实服务

形成能够从浏览器操作的完整产品体验。

  • 将原型核心页面迁移为 React 组件。
  • 把 Dashboard 静态数据切换为真实 API 数据。
  • 接入 AI 任务状态与 SSE 流式进度。
  • 支持报告证据查看、当前任务追问。
  • 支持用户反馈和基本异常状态。
交付： 可运行的 Web MVP 与完整诊断演示链路
WEEK 04MEASURE & IMPROVE

评测、优化和产品复盘

用数据证明或否定产品假设，保留决策依据。

  • 先用 20 条样本验证评测脚本，再扩展至 100 条。
  • 记录诊断分类正确率、引用有效率和成本。
  • 与人工看板分析任务进行小规模对照。
  • 对主要 Bad Case 进行至少一轮迭代。
  • 整理 PRD、原型、评测、版本对比与项目复盘。
交付： 评测报告、迭代记录、面试演示与作品集
04 / ENGINEERING CONTRACT

第一阶段接口与验收

优先落地数据模型和确定性查询，再连接 Agent。接口结构需与 PRD 中的支付尝试统计口径一致。

接口作用验收要点
GET /api/metrics返回 PSR、支付尝试量和趋势筛选维度和统计口径一致
GET /api/metrics/breakdown国家、终端、错误码等维度下钻分类汇总正确、样本量可核对
POST /api/diagnoses创建诊断任务合法参数、任务 ID、权限校验
GET /api/diagnoses/{id}查询诊断任务、状态和报告状态一致，报告可重复获取
GET /api/diagnoses/{id}/events通过 SSE 获取执行进度任务运行、完成和失败事件可靠
POST /api/diagnoses/{id}/feedback提交诊断评价与纠错反馈正确关联任务和版本

最小验收案例 · 德国 Klarna

固定模拟数据 · 非真实业务结果

输入：“分析德国 Klarna 过去 24 小时支付成功率下降的原因。”

89.2%当前支付成功率 · 1784 / 2000
−5.8pp相对 95.0% 基准期下降

• 重点排查维度：Android，当前 PSR 为 85.0%；Web 当前 PSR 为 93.4%。

• Android 端当前失败 150 次，其中 90 次为 redirect_timeout（60%）。

• 需要进一步查询基准错误分布和版本发布记录，不能直接认定 SDK 版本是根因。

验收条件：核心数值均可通过 SQL 独立复算；工具执行与输出报告之间有可追溯的证据链接。
