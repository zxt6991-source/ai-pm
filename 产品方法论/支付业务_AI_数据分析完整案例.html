00 / CASE BRIEF

业务背景：大家开始用了，为什么处理完成的单反而少了？

使用说明：本文参考指定页面的方法路线，另行设计支付业务案例。业务设定、样本、调研发现、实验结果及阈值均为教学模拟，未使用真实业务数据，也不代表读者实际完成过的项目。任务漏斗、商户留存和随机实验是不同样本，分别标明分析单位。

假设你负责一家支付服务商的商户后台。商户运营人员遇到支付失败、退款状态疑问或对账异常时，需要查订单、核对渠道规则，再决定如何处理。产品上线了一个 AI 助手：读取授权范围内的订单状态和规则资料，给出有来源的解释、处理建议和人工转接入口；涉及资金的操作仍走既有授权与审核流程。

本轮只分析入组前即可按规则识别、适合在 24 小时内完成诊断或处置的异常类型。银行侧长期等待等其他任务另建时效指标，范围不能看到结果后再改变。

上线后的两个完整观察周，进入助手的异常单从 1,000 单增至 1,200 单，团队直觉是“需求增长，可以扩大推广”。但经核验的有效处置从 300 单降至 216 单。

任务进入量+20%1,000 → 1,200 单
有效处置量−28%300 → 216 单
整体有效处置率30% → 18%下降 12 个百分点

这次分析必须改变的决策：下一轮资源优先投向新手引导、建议质量、模型升级还是获客？改完之后，达到什么条件才能扩大流量？

分析链条依次回答：成功如何定义 → 哪个因子拖累结果 → 哪一步、哪类任务流失 → 首次价值是否形成持续使用 → 总体变化是否来自客群结构 → 改动是否有效 → 能否持续运行并覆盖成本。方法路线参考原文，以下情节与数值为原创演示。[1]

01 / METRICS

先约定“成功”，再看数据

北极星设为每周 AI 辅助有效处置的去重异常单数。一单需要同时满足：用户明确采纳建议；首次进入助手后 24 小时内完成可核验处置；业务系统与核验流程确认结果；处置后 48 小时内没有重开。人工执行 AI 建议可以计入；转人工后完全独立解决的单另计人工结果。

“复制答案”“继续追问”“生成结束”保留为过程信号。有效处置需要业务结果支持，因此能区分“答案被使用”和“事情被办成”。

层级案例指标支持的判断
北极星周 AI 辅助有效处置单数实际交付的业务价值有没有增加
结果有效处置率、商户 W1/W4 价值留存、处理时长分布、累计贡献毛利业务效率、持续价值和经营表现
过程提交率、结果展示率、建议采纳率、首次有效处置时间具体该改入口、输入、等待还是结果
护栏关键事实错误率、端到端 P95 延迟、每有效处置 AI 成本、严重错误事件改进是否带来质量、体验或成本问题

三个统计单位必须分开

  • 任务漏斗：按 case_id 去重；一个商户可有多单，一单多次生成仍只算一单。
  • 留存：按 merchant_id 去重；成员名单从首用时固定，包含后来没有回来的商户。
  • 成本：汇总所有实际请求，包含重试、失败、未采纳、未解决任务消耗的推理与检索成本。

周漏斗按首次进入助手的自然周归属，业务时区固定为 Asia/Shanghai。每单最多等待 72 小时完成“24 小时处置＋48 小时重开观察”；未成熟周标为暂定，成熟后回填。有效处置量是产品价值指标，不能据此声称这些单全部由 AI 增量创造。

本步产出的决策团队用“有效处置”评估价值，并固定分母、去重、时间窗和成熟条件。后续所有分析共用同一口径。

这份抽样提供的是机制线索，样本比例存在不确定性。“生成后离开”也可能是任务已经完成、暂时没有需求或选择人工，不应全部当成答案质量失败。修复排序还要综合受影响单量、可改善空间、实施成本和错误严重性。

同时保留重试、回流和人工转接

真实流程允许用户补充信息、再次生成或转人工。因此任务漏斗统计“该单是否最终走到某一步”，另看首轮成功率、平均重试次数、等待中退出率、结果展示后退出率和人工接管率。重试不增加任务漏斗分子，但每次请求都增加成本。

本步产出的决策第一轮验证“带订单上下文和有效规则证据的处置卡片”。输入预填与第一单引导留待下一轮独立验证；继续追问次数上升不能直接当成成功。
05 / RETENTION & ACTIVATION

一次有用之后，商户是否会继续使用？

本案例假设商户按周处理若干异常任务，因此主看周价值留存。首次进入真实任务的时间记为 t₀；按首用自然周组建固定同期群，但每个商户的留存窗口统一按首用后的相对天数计算：

  • W0：[t₀, t₀＋7 天)。
  • W1：[t₀＋7 天, t₀＋14 天)。
  • W2：[t₀＋14 天, t₀＋21 天)；W4：[t₀＋28 天, t₀＋35 天)。
  • 回访事件：窗口内至少完成一次有效处置，按处置完成时间归属，并等待之后 48 小时的重开核验。
W1 价值留存率
＝同一首用批次中，在 W1 至少完成一次有效处置的商户数
÷该首用批次全部商户数

看曲线时，早期大幅下降提示需要检查首次体验，后期平台提示存在持续使用人群，周期性回升则要对照任务周期或运营活动。仅凭曲线形状不能确认某一个原因。

寻找候选激活动作

取一个独立的 1,000 家首用商户批次 D。将“首用 24 小时内完成第一次有效处置，随后通过核验”设为候选激活动作，比较之后的 W1 留存：

完成候选激活动作40018045.0%

可提出的假设：帮助新商户尽快完成第一单，可能提升后续留存。具体可测试从真实异常单直接进入、自动带入允许使用的字段、给出场景模板，以及展示第一单的清晰处理路径；同时记录从首次进入到首次价值的时间。

需求强度、商户熟练度和任务难度都可能同时影响激活与留存，因此 45% 与 13.3% 的差异只能产生假设，不能直接当作引导功能的预期增幅。

新增商户、持续活跃商户和沉默至少四周后回流的商户分别观察，避免混合比例掩盖变化。对于当周没有异常任务的商户，可补充“有处理机会的商户继续使用率”；固定同期群价值留存仍保留，以免改变分母后失去可比性。

本步产出的决策将“首次有效处置”作为激活假设，把第一单引导列入后续实验；以周窗口和需求机会辅助解释留存。

07 / CONTROLLED EXPERIMENT

让改动接受验证，再决定推广

前面的分析给出优先级和解释候选。要验证处置卡片的影响，设计同期随机对照；合理的随机化和实验设计为因果判断提供依据。[3]

实验设计项本案例约定
被验证的假设基于最新订单状态与有效规则、展示依据和操作步骤的处置卡片，可提高首单有效处置率
对照与实验A：原建议卡片；B：新版处置卡片。模型版本、入口和新手引导保持一致
入组与分流首次进入合格异常单助手时、看到任何实验内容前入组；按 merchant_id 1:1 随机固定分组，按预设渠道等分层
主要终点每家商户入组的第一张合格异常单是否有效处置；全部入组商户按原始分组进入分母，包括未提交、未采纳者
样本与期限双侧 α＝0.05、80% 检验效能、基线 18%、希望检测至少 3 个百分点，正态近似约需每组 2,737 家；计划每组 3,000 家
观察安排预设完整两周招募、每组至少 3,000 家，等待最后样本成熟；不足样本则按预设整周规则延长，不根据中途显著性任意提前结束
扩大条件点估计提升至少 3 个百分点、95% 区间下界高于 0，并通过预先设定的质量、延迟和成本护栏

之所以每家只取第一张单作为主要检验，是为了让分流单位与分析单位匹配。同一商户的后续多张单用作辅助分析；若纳入推断，需要处理商户内相关性。实验结果识别这套处置卡片组合的效果，不能拆成每个子功能各自的贡献。

本步产出的决策模拟结果支持扩大试验覆盖范围，并在新增覆盖商户中保留随机对照；具体档位按预先制定的放量计划执行。W4 留存和更长窗口的贡献毛利成熟后，再评估持续价值；首单改善暂不等于长期留存已经提升。
08 / MONITORING

把分析变成每周都能执行的管理机制

看板分为总览、过程和明细三层。初始只放 9 类主指标，详细错误分布、时延、成本分布和人工接管放到下钻页面。

看板层指标口径与动作
总览①周有效处置量；②整体有效处置率；③新商户 W1/W4 价值留存每个数标样本量、成熟状态；产品负责人每周判断价值与持续使用
过程④提交率；⑤展示率；⑥采纳率按任务类型、首用渠道、新老商户、模型／检索版本下钻，定位具体责任环节
质量与经营⑦关键事实错误率及严重事件；⑧端到端 P95；⑨每有效处置 AI 成本质量抽检按样本标分母；性能与成本由服务、请求账单和任务事实表关联

指标字典记录定义、分子、分母、时间窗、数据源、刷新频率和负责人。采集类信号可分钟级刷新，转化等成熟指标按天回填，周留存按窗口成熟更新。

一次模拟告警如何处理

  1. 先确认数据。采纳率突然降低，检查事件上报、管道延迟、时区、样本量和核验是否成熟。
  2. 拆群体。发现下降集中在某支付渠道的退款异常，其他类型没有同步下降。
  3. 对照改动。检查该渠道规则版本和检索索引更新，提出“当前规则未被正确召回”的假设。
  4. 验证机制。抽样核对证据，用同一任务重放新旧检索路径；安全范围内再做同期小流量对照。
  5. 采取动作。证实异常后回退相关检索配置、修复索引，监控采纳和有效处置恢复情况。

阈值需要从历史波动、最低样本量和业务容忍度设置。教学示例可采用“同渠道同类任务采纳率较可比基线低 8 个百分点，且连续两个窗口各有至少 200 单”触发调查；这只是排查信号，不自动证明产品退化。确认的严重错误立即走处置流程。

本步产出的决策看板上的每个异常都有负责人、排查入口和后续动作；按成熟窗口比较，避免被未完成观察的数据误导。
09 / EVALUATION LOOP

把流失证据送回评测，再决定是否换模型

badcase 采用风险与影响共同分级

级别本案例中的例子处理与回流
P0对资金状态作出关键错误判断，或建议越权操作确认后立即限制受影响路径、人工接管、修复并加入必过专项回归；低频也可为 P0
P1高频退款场景遗漏当前渠道规则，持续导致未采纳进入下一迭代修复和重点评测，跟踪场景有效处置率
P2低影响长尾表达、结构或格式问题批量处理并纳入周期性回归

每条样本记录任务类型、上下文、输出、引用证据、用户修改、业务结果、错因与版本。将用于开发调试的样本和独立回归测试样本分开，避免只记住已经修过的题；补充正常成功样本，防止回流集合只代表投诉用户。

线上未采纳／错误结果 → 复核标注 → 错因分级 → 修复 → 独立回归 → 小流量上线 → 线上有效处置与护栏复查

模型总体得分更高，是否就值得替换？

再设一个独立的模型替换评估。M1 与 M2 在同一套 1,000 条脱敏任务上盲评，其中 200 条属于关键支付状态判断子集。以下均为模拟结果。

离线评测项M1M2
全量任务通过率910/1,000＝91%940/1,000＝94%
关键支付状态子集194/200＝97%184/200＝92%

M2 的平均分提高，但关键业务子集退化，需要逐条复核差异和严重程度。按预先设置的关键场景门槛，当前不扩大替换。修复并通过回归后，再以固定商户分组测试模型差异，保持处置卡片等产品配置一致。

线上模型比较同时看有效处置率、质量错误、端到端延迟和每有效处置成本；新旧两组跟踪同龄 W1/W4 留存。离线回放和跨时间同期群用于找问题，模型的增量效果仍由恰当设计的同期对照检验。[3]

本步产出的决策先解决业务关键场景的退化，再进入模型灰度；用线上坏例和业务结果更新评测分布。
10 / REVENUE COHORTS

最后检查：留得住，也要算清成本

另取一批已完整观察四周的 100 家开通商户，按首用批次固定成员。统计截至第四周的累计确认收入，并扣除该批次产生的推理、检索及可归属直接服务支持成本。

四周累计项目金额
AI 增值服务确认收入20,000 元
推理与检索成本3,000 元
直接服务支持等可归属变动成本5,000 元
累计贡献毛利12,000 元
该批 100 家商户平均贡献毛利120 元／家

若该批获客支出为 10,000 元，CAC 为 100 元／家，这组教学数据中四周贡献毛利已覆盖获客支出。分母仍为原始 100 家，包含后来不再使用的商户。

再做一个成本情景：如果模型更换后推理与检索成本升到 9,000 元，收入和其他成本暂时不变，则贡献毛利变成 6,000 元、60 元／家，四周内尚未覆盖同样的 CAC。

这是“截至第四周的累计贡献毛利”，尚未代表生命周期 LTV；本例扣除的是所列可归属变动成本，不包括全部研发及管理等固定开支，因此也不等于最终利润。成本变化情景不是已完成的模型实验结果。

本步产出的决策模型、渠道和推广预算以同龄队列的贡献表现复核；收入、增长和推理成本放在一起解释。

APPENDIX / REPRODUCIBLE METRICS

SQL 与 BI：让指标可以复核

数据加工链路为：原始事件与业务状态 → 清洗及有效路径重建 → 任务／商户事实表 → 统一指标 → 按维度下钻的看板。BI 中“数据源”对应事实表，“指标”对应计算口径，“维度”对应渠道、任务类型和版本，“仪表盘”组织这些结果。

A. 从一单一行事实表核对漏斗

下面是通用 SQL 示意，:cohort_start 等为调用侧绑定参数。前提是事实表已按有效事件顺序与窗口构造 reached_stage：1 进入、2 提交、3 看到、4 采纳、5 有效处置；一单只能有一行。mature_after 固定为首次进入后 72 小时。原始多轮事件需要先重建合法路径，不能各取最早时间后假定已经满足顺序。

SELECT
  COUNT(*) AS entered_cases,
  SUM(CASE WHEN reached_stage >= 2 THEN 1 ELSE 0 END)
    AS submitted_cases,
  SUM(CASE WHEN reached_stage >= 3 THEN 1 ELSE 0 END)
    AS viewed_cases,
  SUM(CASE WHEN reached_stage >= 4 THEN 1 ELSE 0 END)
    AS adopted_cases,
  SUM(CASE WHEN reached_stage >= 5 THEN 1 ELSE 0 END)
    AS effective_cases,
  SUM(total_ai_cost) /
    NULLIF(SUM(CASE WHEN reached_stage >= 5
                    THEN 1.0 ELSE 0 END), 0)
    AS ai_cost_per_effective_case
FROM payment_ai_case_fact
WHERE is_eligible = 1
  AND first_entered_at >= :cohort_start
  AND first_entered_at < :cohort_end;
-- 调用前检查该完整周期：MAX(mature_after) <= :as_of。
-- 如未全部成熟，整期标为暂定，不删掉未成熟单后冒充完整周。
-- total_ai_cost 包含该任务截至核算截点的全部请求与重试成本。

用于推断的实验成本必须约定相同归集窗口。本例实验表使用首单进入后 72 小时内的全部 AI 请求成本；业务周报可另做账期成本，但两者不能混用。

B. 固定商户分母，计算同期群 W1 留存

merchant_retention_fact 按商户一行，保留首用时的同期群、渠道、窗口成熟标志和价值回访结果。只有整组完成观察与核验才输出留存率。

SELECT
  first_use_cohort_week,
  channel_at_first_use,
  COUNT(*) AS merchants,
  CASE WHEN MIN(w1_matured) = 1
       THEN SUM(w1_value_retained) * 1.0 / COUNT(*)
       ELSE NULL
  END AS w1_value_retention
FROM merchant_retention_fact
GROUP BY first_use_cohort_week, channel_at_first_use;
-- w1_matured、w1_value_retained 为非空的 0/1 字段。
-- w1 窗口为个人首用后的第 7–13 天，并等待处置后 48 小时核验。
-- 不要通过只保留活跃商户来“清洗”这张表。

统计前还需核对主键唯一、阶段人数嵌套、与业务核验数量一致、版本字段齐全。转化率连乘能检查算术一致性，不能替代事件准确性核查。
